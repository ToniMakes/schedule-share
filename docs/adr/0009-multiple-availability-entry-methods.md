# ADR 0009: 多种可用时间添加方式

## 状态

建议采用。

## 背景

用户提出希望把课表图片识别作为添加日程的一种方法，而不是唯一方法。这个方向也符合竞品观察：

- When2meet 的核心价值是拖拽格子和群体重叠热力图。
- Doodle 和 Rallly 更偏候选时间投票，组织者先给出若干选项，参与者选择方便与否。
- LettuceMeet 延续可用性网格，并强调移动端和日历辅助。

因此，本项目不应被定义成某一种填写 UI，而应定义成“多种来源的可用时间收集和归一化工具”。

## 决策

所有添加方式都必须先转换成统一的可用时间草稿，再由用户确认提交。

- `Availability` 仍然是系统的最终数据：参与者确认后的可用时间槽。
- 不同添加方式只负责生成 `AvailabilityDraft`，不能直接写入最终提交。
- 核心时间计算仍放在 `packages/core`，包括时间格生成、忙碌时间求差集、模板投影、候选时间对齐和结果统计。
- UI 可以提供多个添加入口，但最终都回到同一个确认界面和同一个提交 API。
- 没有登录的用户也必须能使用手动拖拽和基础图片/文本导入。
- 登录只增强长期模板、历史昵称、默认时区和未来跨设备同步。

## 添加方式优先级

### P0：手动拖拽网格

吸收 When2meet 的低摩擦体验：

- 参与者在日期 x 时间格上拖拽选择自己有空的时间。
- 同一页面展示个人选择和群体重叠结果。
- 移动端需要支持点按、拖动或分段选择。
- MVP 已具备可用时间槽提交能力，后续重点是把交互体验打磨成更顺手的网格。

### P1：图片和文本导入

延续 ADR 0008：

- 上传课表截图、排班截图或粘贴日程文本。
- 系统识别忙碌时间，反推出当前活动内的可用时间草稿。
- 用户必须确认或修正后提交。

### P1：个人长期可用模板

延续 ADR 0008：

- 登录用户保存自己的长期有空时间。
- 参与活动时把模板投影到活动日期范围和时间粒度。
- 用户确认后提交。

### P2：候选时间投票模式

吸收 Doodle/Rallly 的组织者候选选项模式：

- 组织者不是开放一整段时间网格，而是先列出几个候选时间段。
- 参与者只需选择每个候选时间是否方便。
- 后续可支持 `available`、`maybe`、`unavailable` 或偏好权重。
- 该模式适合正式会议、面试、讲座、饭局订位等候选时间有限的场景。

### P2：文件和日历轻导入

在真实需求出现后再做：

- `.ics` 文件导入忙碌时间。
- CSV 或表格粘贴导入固定排班。
- 导出最终时间到日历文件。

暂不优先做完整 Google Calendar、Outlook 或 Apple Calendar OAuth 深度同步，因为它会显著提高认证、隐私、合规和维护成本。

### P3：复用和智能默认

适合高频用户：

- 克隆上一次活动设置。
- 使用历史昵称和默认时区。
- 根据用户过去提交生成可编辑建议，但必须明确提示并允许关闭。

## 不采用或后置

- 不在短期内做完整预订页、收费预约、票务报名或签到表。
- 不把广告放进核心填写操作之间。
- 不为了某一种导入方式新增平行业务模型。
- 不保存原始图片、原始日历文件或未确认识别结果作为默认行为。

## 架构影响

建议形成统一管线：

```text
input method -> adapter -> AvailabilityDraft -> confirmation UI -> participant submit API -> Availability
```

- `packages/core` 负责把各种时间来源映射到当前日程时间格。
- `apps/web` 负责不同输入方式的交互和确认界面。
- `packages/api-client` 负责各输入方式的请求/响应契约。
- `packages/db` 短期只保存最终提交；只有长期模板、账号或候选时间模式上线时才新增表结构。

## 结果

优点：

- 产品不被单一竞品形态限制。
- 用户可以按自己的场景选择最快的填写方式。
- 未来增加新输入方式时，仍能复用核心统计和提交链路。
- 更容易体现差异化：轻量群体排期 + AI 导入 + 长期模板。

代价：

- UI 信息架构会更复杂，需要明确默认入口和渐进展开。
- 候选时间投票和偏好权重会扩展当前二元可用时间模型。
- 不同导入来源的错误和置信度提示需要统一设计。

## 后续检查

当出现以下情况时重新评估：

- 用户主要使用候选投票，而不是开放网格。
- 用户要求 `maybe`、偏好权重或不同参与者权重。
- 日历 OAuth 成为高频需求。
- 微信小程序入口要求完全不同的填写交互。
- 多输入入口让新用户创建或填写变慢。
